# Qwen3-ASR 模型与路数真实性能报告

## 测试方法

- 开发板：K3/A100，Python 3.13.12，项目提交 `4787eca`。
- 输入：`~/Music/wav16k`。每个组合连续运行 3 次、串行执行；每次重新加载 Zipformer 和共享 Qwen3-ASR。
- 组合：Qwen3-ASR 0.6B q40 的 2/4/6/8 路，Qwen3-ASR 1.7B q4km 的 2/4 路。
- 8 路时，现有输入选择逻辑会循环使用该目录中的 6 个 WAV 文件。
- 每次检查每路最终结果、model output 六字段、Zipformer/Qwen sentence ID 和 lane 最终状态。

## 功能校验

全部 18 个 run 的 Zipformer/Qwen `sentence_id` 集合均一致，没有请求丢失或 ID 错配。

以下两个 0.6B/8 路 lane 的最后一个 Qwen final 返回空字符串：

- `process-1783872846707`：lane1，空文本 `sentence_id=63`。
- `process-1783873490924`：lane7，空文本 `sentence_id=61`。

`results/laneN.txt` 会为该 final 写入空行；基准完整性脚本过滤空行后，将“Qwen 记录数与非空文本行数不同”与 ID 集合检查合并标记为 `sentence alignment invalid`。因此此前报告中的“sentence ID 不一致”表述不准确，已更正。

两个 lane 分别出现 120 和 123 个丢帧。代码中 `OnlineFrameQueue(maxsize=1)` 在消费者落后时会用最新帧替换未消费帧，而离线 Qwen 使用的是已消费帧累积出的 `SegmentCache` 音频。高丢帧意味着最后一个 endpoint 可能只包含稀疏或非语音片段；现有 artifact 没有保存 Qwen 原始响应，不能进一步证明空文本的模型内部原因，但它与 8 路下的高 queue 时间和高丢帧强相关。

## 结论

- 0.6B q40 的 2 路是最稳定组合：零丢帧、平均在线延迟 33.259ms、RTF 0.266084。
- 0.6B q40 的 4 路仍接近目标：平均在线延迟 41.627ms，平均总丢帧 0.667；RTF 为 0.448518。
- 0.6B q40 的 6/8 路与 1.7B q4km 的 4 路均发生明显丢帧和离线队列积压。0.6B/8 路有两个空 Qwen final，但不存在 sentence ID 错配。
- 1.7B q4km 的 2 路能保持低丢帧，但 RTF 已为 0.822216；4 路不具备当前配置下的稳定实时能力。
- 原始 benchmark artifacts 位于开发板 `runs/qwen3-benchmark-20260712-233347/`，其中包含 manifest、driver log、summary JSON 及全部 18 次 run 目录。

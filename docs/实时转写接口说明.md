# 实时转写接口说明（`/ws/stream`）

---

## 0. 怎么连、带什么参数、怎么开始推音频

### 0.1 连接 URL 与查询参数

```
ws://192.168.1.179:8000/ws/stream?sample_rate=16000&wakeup=false
```

| 查询参数 | 必填 | 默认 | 说明 |
|----------|------|------|------|
| `sample_rate` | 否 | `16000` | 音频采样率（Hz）。推流 PCM 必须与此一致 |
| `wakeup` | 否 | `true` | 是否启用唤醒词门控。纯转写场景建议 **`false`**（连上 `start` 后立刻出字）；`true` 时需先说唤醒词，且默认有限时窗口 |

音频格式固定（不可改）：

- 编码：PCM 有符号 16-bit little-endian（PCM16）
- 声道：单声道（mono）
- 采样率：与 URL 里 `sample_rate` 一致（常用 16000）

### 0.2 连接后时序（必按此顺序）

```text
1. 建立 WebSocket
2. 收到 {"type":"status","status":"ready",...}          ← 可以发控制消息了
3. （可选）发 JSON config → 收到 {"type":"config_ok",...}
4. 发 JSON {"type":"start"} → 收到 {"type":"status","status":"started","lane_id":N}
5. 开始持续发送 二进制 PCM 帧（WebSocket binary）
6. 同时监听下行 JSON（transcript / status / error …）
7. 结束：发 {"type":"finish"} → finalizing → saved? → ready_for_new_transcription
```

要点：

1. **先收到 `ready`，再 `start`，再推二进制音频。** `start` 之前发的 binary 会被丢弃。  
2. **`config` 可选**：URL 已声明 `sample_rate`，且服务端只接受 mono PCM16；不发 `config` 也可以直接 `start`。  
3. 文本帧 = 控制 JSON；二进制帧 = 原始 PCM 字节，**不要**把 PCM 包进 JSON。

### 0.3 客户端 → 服务端：控制消息（Text / JSON）

| `type` | 何时发 | 说明 |
|--------|--------|------|
| `config` | `start` 前，可选，整次连接最多一次 | 声明音频格式 |
| `start` | 准备好推流时 | 分配 lane 并开始识别 |
| `pause` | 已 `started` | 暂停消费音频（仍可连着，binary 会被忽略） |
| `resume` | 已 `paused` | 继续 |
| `finish` / `done` | 要结束本轮 | 收尾、落盘；可选 `"enable_summary": true` |
| `new_transcription` | 上一轮已结束后开新一轮 | 释放旧会话、清缓冲，再等 `start` |

**config 示例：**

```json
{
  "type": "config",
  "sample_rate": 16000,
  "channels": 1,
  "width": 2
}
```

- `sample_rate` 必须等于连接 URL 的 `sample_rate`  
- `channels` 必须为 `1`，`width` 必须为 `2`（PCM16）  
- 成功回 `{"type":"config_ok","lane_id":...}`（此时可能还没有 lane，`lane_id` 可能为 `-1`）

**start / finish 示例：**

```json
{"type": "start"}
```

```json
{"type": "finish", "enable_summary": false}
```

### 0.4 客户端 → 服务端：推音频（Binary）

收到 `status: "started"` 之后，用 **WebSocket binary** 持续发送 PCM16 原始字节。

建议：

- 每包约 **20~100 ms** 音频（16 kHz 单声道 PCM16：100 ms = 3200 字节）
- 按采集节奏连续发，不要攒很大一块再偶发
- `pause` 期间不要依赖服务端缓存未发的话；`finish` 后不要再发 binary

伪代码：

```js
const ws = new WebSocket("ws://192.168.1.179:8000/ws/stream?sample_rate=16000&wakeup=false");
ws.binaryType = "arraybuffer";

ws.onmessage = (ev) => {
  const msg = JSON.parse(ev.data);
  if (msg.type === "status" && msg.status === "ready") {
    ws.send(JSON.stringify({ type: "start" }));
  }
  if (msg.type === "status" && msg.status === "started") {
    // 开始 mic → 每次得到 Int16Array / ArrayBuffer 就：
    // ws.send(pcmArrayBuffer);
  }
  if (msg.type === "transcript") {
    onTranscript(msg); // 见下文覆盖规则
  }
};

// 结束本轮
function stop() {
  ws.send(JSON.stringify({ type: "finish" }));
}
```

### 0.5 服务端 → 客户端：你会收到什么（Text / JSON）

所有下行都是 JSON 文本帧。

| `type` | 含义 | 前端要做什么 |
|--------|------|----------------|
| `status` | 生命周期 | 见下表 `status` 字段 |
| `config_ok` | 格式确认成功 | 可继续 `start` |
| `transcript` | 转写结果（核心） | 按三态覆盖展示（本文 §1~§4） |
| `kws` | 唤醒词命中 | `wakeup=true` 时有用 |
| `speaker_remap` | 会话末说话人标签重标 | 原子套用整张 `mapping` |
| `saved` | 转写已落盘 | `{lane_id, path}` |
| `summary` | 纪要（仅 `finish` 带了 `enable_summary`） | 按需展示 |
| `error` | 错误 | 提示用户；连接可能仍保持 |
| `finished` | lane 侧结束信号 | 一般跟着收尾状态走即可 |

**常见 `status`：**

| `status` | 含义 |
|----------|------|
| `ready` | 已连上，可发 `config` / `start` |
| `started` | 已开始，**可以推 binary PCM** |
| `paused` / `resumed` | 暂停 / 继续 |
| `wakeup` | 已唤醒（`wakeup=true`） |
| `sleep` | 转写窗口到期，回到待唤醒 |
| `finalizing` | 正在收尾（点了 `finish`） |
| `ready_for_new_transcription` | 本轮结束完成，可再 `start` 或 `new_transcription` |

结束时序简述：`finish` → `finalizing` →（可能 `saved` / `summary`）→ `ready_for_new_transcription`。  
不要整页刷新断线；等到 `ready_for_new_transcription` 再开新一轮。

## 1. 三态总表（`type: "transcript"`）

| 阶段 | `is_partial` | `is_final` | 含义 | UI 建议 |
|------|--------------|------------|------|---------|
| 说话中 | `true` | `false` | 流式中间结果，同句会不停刷新 | 灰色 / 弱样式，可滚动更新 |
| 已断句、Qwen 校正中 | `false` | `false` | **pending**：在线句已切好，已送 Qwen3-ASR，尚未返回 | 灰色，可标「校正中」 |
| Qwen 完成 | `false` | `true` | **定稿**：校正结果，应覆盖上一版 | 正常正文色；可显示说话人 |

判定函数：

```js
function phaseOf(msg) {
  if (msg.is_final) return "final";     // 定稿
  if (msg.is_partial) return "partial"; // 流式中
  return "pending";                    // 两 bool 皆 false = 校正中
}
```

> 业务 WS **没有**单独的 `status: "pending"` 字段。  
> **`is_partial === false && is_final === false` 就是 pending。**

## 2. 一条消息长什么样

```json
{
  "type": "transcript",
  "lane_id": 0,
  "sentence_id": 3,
  "revision": 5,
  "is_partial": false,
  "is_final": false,
  "segment": {
    "text": "我们今天讨论一下进度"
  },
  "timestamp_ms": 12840
}
```

| 字段 | 说明 |
|------|------|
| `lane_id` | 通道号 |
| `sentence_id` | 句号；同一句话不变 |
| `revision` | 同句版本号；只处理 **大于** 本地已记录的版本 |
| `segment.text` | 要展示的文本 |
| `segment.speaker` | 说话人信息；**一般只在 `is_final=true` 时出现** |
| `timestamp_ms` | 相对时间戳（毫秒） |

定稿示例（校正完成）：

```json
{
  "type": "transcript",
  "lane_id": 0,
  "sentence_id": 3,
  "revision": 6,
  "is_partial": false,
  "is_final": true,
  "segment": {
    "text": "我们今天讨论一下进度。",
    "speaker": {
      "label": "S1",
      "name": "张三",
      "confidence": 0.82,
      "is_provisional": false
    }
  },
  "timestamp_ms": 12840
}
```

展示说话人时：`name` 有值用 `name`，否则用 `label`。

## 3. 同句时间线（典型）

```text
sentence_id=3

revision=1  is_partial=true   is_final=false   text="我们"          → partial
revision=2  is_partial=true   is_final=false   text="我们今天"      → partial（覆盖）
revision=3  is_partial=true   is_final=false   text="我们今天讨论"  → partial（覆盖）
        … 约 0.7s 尾静音断句 …
revision=4  is_partial=false  is_final=false   text="我们今天讨论一下进度" → pending（校正中）
        … Qwen 推理 约 0.5~数秒 …
revision=5  is_partial=false  is_final=true    text="我们今天讨论一下进度。" → final（定稿覆盖）
```

实际条数不一定这么多：partial 可能很少，也可能几乎直接到 pending。

## 4. 怎么落地

### 4.1 覆盖规则（必做）

```js
const revisions = new Map(); // key -> 已接受的最大 revision
const rows = new Map();      // key -> 行数据 / DOM

function onTranscript(msg) {
  const key = `${msg.lane_id}:${msg.sentence_id}`;
  const prev = revisions.get(key) ?? -1;
  if (msg.revision <= prev) return; // 丢弃乱序/过期
  revisions.set(key, msg.revision);

  const phase = phaseOf(msg);
  const text = msg.segment?.text ?? "";
  const speaker = msg.is_final ? msg.segment?.speaker : undefined;

  upsertRow(key, { text, phase, speaker });
}
```

要点：

1. **同一 `sentence_id` 只保留一行**，不要每条消息新开一行。  
2. **`revision` 必须单调前进**，旧包直接丢。  
3. pending → final 时改样式 + 换文本，不要另起一行。

### 4.2 样式建议

```css
.utterance.partial,
.utterance.pending { color: #888; }
.utterance.pending::after { content: " · 校正中"; font-size: 12px; opacity: 0.8; }
.utterance.final { color: #111; }
```

### 4.3 和落盘的关系

| 内容 | 是否进历史文件 `output/transcripts/*.txt` |
|------|------------------------------------------|
| partial | 否 |
| pending | 否 |
| final | **是**（正式转写只收定稿） |

页面上可以一直显示 pending；刷新历史列表时只会看到 final。

## 5. 边界情况

| 情况 | 表现 | 建议 |
|------|------|----------|
| Qwen 失败 | 可能长期停在 pending，或收到 `type:"error"` | pending 保留，或标「校正失败」 |
| 句太短 / 噪声 | 可能没有 pending/final | 无行可忽略 |
| 乱序到达 | 低 `revision` 后到 | 用 revision 丢弃 |
| 声纹未开 | final 也没有 `speaker` | 只显示文本 |
| 会话末 `speaker_remap` | 改标签映射 | 原子整表替换已展示的 label（见声纹文档） |
| `start` 前推了 PCM | 服务端直接丢弃 | 等 `started` 再推 |
| `wakeup=true` 未唤醒 | 听得见但没有 `transcript` | 纯转写请用 `wakeup=false` |

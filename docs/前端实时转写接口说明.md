# 前端实时转写：结果三态说明

适用：`/ws/stream`、`/ws/multicast`（及同类）下行的 `type: "transcript"` 消息。

每句话会推送多次。前端用 **`lane_id + sentence_id`** 当作同一行的稳定 ID，用更高的 **`revision`** 覆盖旧内容。

---

## 1. 三态总表

| 阶段 | `is_partial` | `is_final` | 含义 | UI 建议 |
|------|--------------|------------|------|---------|
| 说话中 | `true` | `false` | 流式中间结果，同句会不停刷新 | 灰色 / 弱样式，可滚动更新 |
| 已断句、Qwen 校正中 | `false` | `false` | **pending**：在线句已切好，已送 Qwen3-ASR，尚未返回 | 灰色，可标「校正中」 |
| Qwen 完成 | `false` | `true` | **定稿**：校正结果，应覆盖上一版 | 正常正文色；可显示说话人 |

判定函数：

```js
function phaseOf(msg) {
  if (msg.is_final) return "final";     // 定稿
  if (msg.is_partial) return "partial"; // 流式中
  return "pending";                    // 两 bool 皆 false = 校正中
}
```

> 业务 WS **没有**单独的 `status: "pending"` 字段。  
> **`is_partial === false && is_final === false` 就是 pending。**

---

## 2. 一条消息长什么样

```json
{
  "type": "transcript",
  "lane_id": 0,
  "sentence_id": 3,
  "revision": 5,
  "is_partial": false,
  "is_final": false,
  "segment": {
    "text": "我们今天讨论一下进度"
  },
  "timestamp_ms": 12840
}
```

| 字段 | 说明 |
|------|------|
| `lane_id` | 通道号 |
| `sentence_id` | 句号；同一句话不变 |
| `revision` | 同句版本号；只处理 **大于** 本地已记录的版本 |
| `segment.text` | 要展示的文本 |
| `segment.speaker` | 说话人信息；**一般只在 `is_final=true` 时出现** |
| `timestamp_ms` | 相对时间戳（毫秒） |

定稿示例（校正完成）：

```json
{
  "type": "transcript",
  "lane_id": 0,
  "sentence_id": 3,
  "revision": 6,
  "is_partial": false,
  "is_final": true,
  "segment": {
    "text": "我们今天讨论一下进度。",
    "speaker": {
      "label": "S1",
      "name": "张三",
      "confidence": 0.82,
      "is_provisional": false
    }
  },
  "timestamp_ms": 12840
}
```

展示说话人时：`name` 有值用 `name`，否则用 `label`。

## 3. 同句时间线（典型）

```text
sentence_id=3

revision=1  is_partial=true   is_final=false   text="我们"          → partial
revision=2  is_partial=true   is_final=false   text="我们今天"      → partial（覆盖）
revision=3  is_partial=true   is_final=false   text="我们今天讨论"  → partial（覆盖）
        … 约 0.7s 尾静音断句 …
revision=4  is_partial=false  is_final=false   text="我们今天讨论一下进度" → pending（校正中）
        … Qwen 推理 约 0.5~数秒 …
revision=5  is_partial=false  is_final=true    text="我们今天讨论一下进度。" → final（定稿覆盖）
```

实际条数不一定这么多：partial 可能很少，也可能几乎直接到 pending。

## 4. 前端怎么落地

### 4.1 覆盖规则（必做）

```js
const revisions = new Map(); // key -> 已接受的最大 revision
const rows = new Map();      // key -> 行数据 / DOM

function onTranscript(msg) {
  const key = `${msg.lane_id}:${msg.sentence_id}`;
  const prev = revisions.get(key) ?? -1;
  if (msg.revision <= prev) return; // 丢弃乱序/过期
  revisions.set(key, msg.revision);

  const phase = phaseOf(msg);
  const text = msg.segment?.text ?? "";
  const speaker = msg.is_final ? msg.segment?.speaker : undefined;

  upsertRow(key, { text, phase, speaker });
}
```

要点：

1. **同一 `sentence_id` 只保留一行**，不要每条消息新开一行。  
2. **`revision` 必须单调前进**，旧包直接丢。  
3. pending → final 时改样式 + 换文本，不要另起一行。

### 4.2 样式建议

```css
.utterance.partial,
.utterance.pending { color: #888; }
.utterance.pending::after { content: " · 校正中"; font-size: 12px; opacity: 0.8; }
.utterance.final { color: #111; }
```

### 4.3 和落盘的关系

| 内容 | 是否进历史文件 `output/transcripts/*.txt` |
|------|------------------------------------------|
| partial | 否 |
| pending | 否 |
| final | **是**（正式转写只收定稿） |

页面上可以一直显示 pending；刷新历史列表时只会看到 final。

## 5. 边界情况

| 情况 | 表现 | 前端建议 |
|------|------|----------|
| Qwen 失败 | 可能长期停在 pending，或收到 `type:"error"` | pending 保留，或标「校正失败」 |
| 句太短 / 噪声 | 可能没有 pending/final | 无行可忽略 |
| 乱序到达 | 低 `revision` 后到 | 用 revision 丢弃 |
| 声纹未开 | final 也没有 `speaker` | 只显示文本 |
| 会话末 `speaker_remap` | 改标签映射 | 原子整表替换已展示的 label（见声纹文档） |

## 6. 结束转写（外部前端必看）

点结束（`finish`/`done`）后，服务端会：

1. 立刻下发 `{"type":"status","status":"finalizing"}` —— **请用这个结束「转圈/加载中」的死等感**（表示正在收尾，不是卡死）。
2. 约数秒到几十秒内（默认宽限约 25s）排空/取消积压校正。
3. 可能下发 `saved` / `summary`。
4. 最终下发 `{"type":"status","status":"ready_for_new_transcription"}` —— 才算结束完成，可开新一轮。

若超时：可能先收到 `error`（如 `transcription finish timed out`），仍应尽量等到 `ready_for_new_transcription`；WebSocket **一般保持连接**，不要整页刷新，重发 `start` / `new_transcription` 即可。

长会议（1~2 小时）结束时，未校正完的 pending 句可能来不及全部变成 final（服务为避免卡死会取消积压）；已 final 的句子不受影响。

组播（`/ws/multicast`）：任务跨 WS 断线保活，转写缓冲在任务上而不在连接上。断线期间的 final 仍会累积；重连后服务端会回放已定稿句子；点结束落盘的是整场任务全文，不是「本条连接见过的尾巴」。

---

## 7. 联调自检

1. 说话时：同句反复更新，且 `is_partial=true`。  
2. 停顿后：出现 `is_partial=false && is_final=false`，样式与 final 不同。  
3. 稍后：同 `sentence_id`、更高 `revision`、`is_final=true`，覆盖 pending。  
4. 点结束：先收到 `finalizing`，再收到 `ready_for_new_transcription`（不应一直无状态）。  
5. 结束后拉历史：文件里只有定稿句，没有「校正中」中间态。

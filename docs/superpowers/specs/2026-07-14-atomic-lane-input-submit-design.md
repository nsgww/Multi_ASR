# Lane 输入原子提交设计

## 问题

模型已加载时，前端对每个 Lane 输入变化立即发送完整的 `lane_inputs`。请求虽然按队列执行，但控件闭包仍引用请求前的旧对象；服务器响应替换数组后，后续控件修改可能写入旧对象。快速选择两路麦克风时，最终配置可能只保留第一路麦克风。

## 目标

模型生命周期只锁定路数和模型配置。音频输入保持为独立的前端草稿，在识别真正开始前可以随时修改，包括模型加载期间以及一次识别自然结束或手动终止之后。

## 设计

- Lane 输入控件只修改 `appState.draft.laneInputs`，不在每次选择变化时请求后端，也不随模型加载请求提交。
- 点击 `Start recognition` 后，前端先向 `/api/lane-inputs` 一次性提交当前完整草稿。
- `/api/lane-inputs` 成功后，前端再调用 `/api/recognition/start`。
- 任一步骤失败都不启动识别；保留上一轮识别结果，并显示后端返回的配置错误。
- `/api/models/load` 只接收路数和模型配置，不读取或校验 Lane 输入。
- 后端将模型文件校验和音频输入校验拆开。模型加载只校验模型文件；开始识别时校验完整 Lane 输入。
- 麦克风、Local WAV 和默认文件都在启动状态切换前完成验证。验证失败时管理器保持 `loaded`，不创建新 run，也不向 Lane 进程发送启动命令。

## 麦克风列表

- `GET /api/audio-devices` 继续由主服务进程提供，不依赖 Lane 进程，也不依赖识别是否运行过。
- 模型加载是异步流程，不能阻塞主服务处理麦克风列表请求。
- 前端不缓存麦克风设备列表。每次用户把某一路输入类型选择为 `Microphone` 时，都重新请求 `/api/audio-devices` 并更新该路设备下拉框。
- 查询失败时显示错误并保留该路麦克风选择；开始识别仍会重新执行设备可用性验证。

## 状态与交互

- 模型加载和卸载只锁定路数、离线模型类型及模型路径。
- `unloaded`、`loading`、`loaded`、`unloading` 和 `fatal` 状态允许编辑 Lane 输入草稿。
- `starting`、`running` 和 `stopping` 状态锁定 Lane 输入。
- 开始按钮处理期间立即禁用，防止重复提交。
- 成功启动后才清空上一轮识别视图。
- 识别自然结束或手动终止并回到 `loaded` 后，Lane 输入立即恢复可编辑；下一次开始时重新提交当前完整草稿。

## 测试

- 前端结构测试确认控件变化不再调用 `/api/lane-inputs`。
- 前端结构测试确认开始流程先提交完整 `lane_inputs`，再调用 `/api/recognition/start`。
- 前端测试确认模型加载期间 Lane 输入可编辑，而路数和模型配置不可编辑。
- 前端测试确认每次切换到麦克风都会重新请求设备列表，不复用旧缓存。
- API 测试确认完整的“两路麦克风 + 两路默认文件”配置保持 Lane 顺序并被管理器接收。
- API 测试确认模型加载不校验旧 Local WAV 输入，且模型加载等待期间麦克风列表接口可以响应。
- 管理器测试确认麦克风、Local WAV 或默认文件验证失败时状态仍为 `loaded`，且没有启动任何 Lane。
- 运行完整测试集，确认模型加载、停止和再次启动行为无回归。
